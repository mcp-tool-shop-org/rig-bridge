### 2. `tldr` validator (parked Phase 0 question Q1)

`docs/envelope-spec.md` §3.2 declares `tldr` as ≤280 chars "soft cap, validator only" but no validator exists in v1.0.0. v1.1 decision required:

- **Option A**: `bridge send` enforces the cap, refusing to send if exceeded
- **Option B**: `bridge send` warns (stderr) but proceeds
- **Option C**: drop the cap from the spec entirely

Pick one in v1.1. Document the choice with reasoning.

### 3. Multi-recipient envelope row count (parked Phase 0 question Q2)

`docs/control-plane-integration.md` §4 cross-walk asserts "multi-recipient envelopes land as one row per recipient at the courier seam." Alternative: one row with `to_rig` as a JSON array.

The choice has indexing + query-shape consequences:
- Per-recipient rows: simple SQL queries (`WHERE to_rig = ?`), but a 5-recipient envelope produces 5 rows
- JSON array: one row per envelope, but `to_rig LIKE '%foo%'` queries are fragile

v1.1 implementor's call when the CP code lands. Document the choice with reasoning.

### 4. `display_name` Unicode handling (parked Phase 0 question Q3)

`schemas/bridge-message.schema.json` enforces `display_name` ≤80 chars but no character-set restriction (Unicode allowed). v1.1 review:

- Does any rendering surface (terminal output, GitHub markdown, control-plane queries) break on non-ASCII display names?
- If yes, restrict the schema. If no, leave open (the field is metadata-only).

This is review, not necessarily a code change.

## Open questions from Phase 7 study swarm (2026-05-15)

The four-agent research-grounded dispatch that informed Phase 7's architectural locks also surfaced four open questions. None block v1.0.0 ship; each is an empirical or design decision deferred to v1.1 (or later) when evidence accumulates.

### OQ1 — Low-volume async sync regime is unstudied

rig-bridge's operating regime (1-10 envelopes/day across 2-4 paired rigs, low write contention, async humans-in-the-loop) is not directly studied in the conflict-resolution literature. The locks chosen for `sync` (L1-L4: surface every non-FF, never silent-merge content) extrapolate from OSS / Microsoft-scale findings (Owhadi-Kareshk 2019, Tao 2021) which describe much higher-volume regimes.

v1.0.0 defaults to **always surface non-FF**. v1.1 may relax this if dogfood evidence shows the surface-rate is dominated by trivially-resolvable cases. The empirical question: what fraction of non-FF surfaces could a tighter heuristic auto-resolve safely? Until rig-bridge has logged enough cross-rig sessions to answer that, the conservative default holds.

### OQ2 — AI racing human relay needs a "thread-frozen-pending-relay" state

When rig A's agent is mid-thread and the operator on rig B types `relay` to inject a human-attested DECISIONS turn, there's a small race window: rig A's agent may push a new envelope before the relay lands. Per L5-L9, the relay's `in_reply_to: <body_hash>` chain catches the divergence, but the operator-experience is "I tried to relay and got told the chain moved."

Mitigation surface: a "thread-frozen-pending-relay" state — when an operator starts a relay, the thread is soft-locked for non-relay sends until the relay turn lands or a timeout expires. Defer the empirical validation + implementation slice to **v1.0.1**; v1.0.0 ships with the chain check as the only guard.

### OQ3 — `--output={text,json,ndjson}` triad vs binary `--json`

The Phase 7 finding 27 (kubectl `-o {name,json,yaml,jsonpath}` triad) suggests a multi-mode output flag could be cleaner per-invocation than the binary `--json` flag rig-bridge ships in v1.0.0. Watch-mode wants NDJSON (one JSON per line); one-shot wants a JSON object; text mode is the default.

v1.0.0 ships **binary `--json`** with NDJSON **inferred** when `--watch` is added (currently `--watch` is not implemented). v1.1 may evolve to the explicit triad if downstream tooling demonstrates the triad is more ergonomic. The contract in [`cli-contract.md`](cli-contract.md) §2 is the pin-point — additive triad is minor-compatible, removing `--json` is not.

### OQ4 — CLI-specific eye-tracking absent; 5-column status cap is extrapolated

The 5-column cap for `status` default output (L10, finding 17 Cowan 2001 + finding 24 Long 2024) extrapolates from dashboard + working-memory studies; no eye-tracking research specifically measures CLI table scanning. Long et al. 2024 (dashboard-overload, piecewise-linear effect with 2 knots at 4 and 9 modules) is the closest empirical anchor.

v1.0.0 ships the 5-column cap with `--wide` as the single progressive-disclosure tier (L11). v1.1 may revisit if dogfood evidence shows operators consistently invoke `--wide` (suggesting the default is too narrow) or skip columns (suggesting it's too wide). The single disclosure level is itself locked per Nielsen 2006; v1.1 will not add a third tier.

## Out of scope for v1.1

- Multi-rig (3+) topology — symmetric two-rig is still the v1.x model
- MCP frontend — `bridge` is CLI-only through v1.x
- Cloud-hosted central queue — git remains the wire
- Encryption beyond GitHub TLS — repo permissions are the auth model

These remain out of scope per `docs/envelope-spec.md` §7 and `ARCHITECTURE.md` "Out of scope for v1.0.0". v1.1 inherits all v1.0.0 deferrals.

## v1.0.0 boundary — what v1.0.0 ships

For clarity (8 of 8 commands shipped as of Phase 7):

Authoring:
- `rig-bridge init` — initialize local clone, install commit-message hook, write `.bridge/config.yaml`
- `rig-bridge new <thread-id>` — scaffold from template
- `rig-bridge send <type> --thread <id>` — validate + body_hash + marker→class derivation + canonical rig-id ingress + git commit + push (NO control-plane write)
- `rig-bridge close <thread-id>` — write `RESOLUTION.md` + commit + push (NO control-plane write)

Inspection:
- `rig-bridge status` — list open threads with last/status/type/dirty (with `--json` + `--wide` opt-ins)
- `rig-bridge thread <id>` — render the full envelope transcript (small-multiples, chronological asc)

Sync + attestation:
- `rig-bridge sync` — fast-forward pull with named divergence surfacing
- `rig-bridge relay <type> --thread <id> --in-reply-to <hash>` — human-attested DECISIONS/RESPONSE/ACK turn

Engine helpers: envelope parse/render, schema validation, body_hash with §4.1 normalization, status_class derivation, rig-id validation, git wrapper with submodule + size guards, plus the 5 Phase 7 additions (`listThreads`, `findPeerRigs`, `gitDiffSinceLastSync`, `verifyHash`, `validateEnvelopeFile`).

CLI contract: stdout/stderr discipline, `--json` opt-in with `schema_version: "1.0"`, exit codes, env vars — see [`cli-contract.md`](cli-contract.md).

That's the complete v1.0.0 product surface. Phase 8 adds guards. Phase 10 ships v1.0.0 via Full Treatment.

v1.1 begins the moment testing-os ships its next schema bump.
